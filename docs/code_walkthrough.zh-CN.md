# 一条案例如何穿过代码

前置只需读 [中文入口](../README_CN.md)。这篇按“数据 → 方法 → 串联 → 评估”讲，
不是按文件树逐个介绍。文中例子用于解释逻辑，不是新增实验结果。

## 1. 输入先分清：问题、候选、答案是三样东西

`models.py` 的 `EntityCase` 保存一条实验题目，包括：

```text
case_id           唯一题号，例如 homonym_002
surface_form      文本写出的名字，例如 Mercury
context           此处的使用语境
source_triple     携带关联信息的来源三元组
 gold_entity_id    对照答案，例如 Q925（不发送给消歧器）
```

当前数据的 `source_triple` 用 `describedInContext` 携带同一段上下文，二者信息重复。
因此这个原型只能比较“有这组上下文 / 无上下文”，**不能声称已经分离验证了句子上下文和关系三元组各自的贡献**。

`Candidate` 是检索返回的候选，包含 QID、标签、别名、描述、来源。
`Resolution` 是模型或规则返回的选择，包含 QID/null、confidence 和简短理由。
拟定的 gold 不能混进 Candidate，也不能放进发给模型的 payload。

Pydantic 做什么？`confidence=-3` 或 `selected_entity_id="ABC"` 这样的结果会被拒绝。
它不知道 Q925 是否真的适合这里，所以“格式正确”与“事实正确”必须分开评估。

## 2. 最简单的方法：StringBaseline.resolve

文件：`src/llm_knowledge_audit/disambiguation/string_baseline.py`。

逻辑可以压缩为：

```text
把名字做 Unicode 标准化、大小写统一、标点处理
对每个候选的标签和别名计算字符串相似度，取其最高值
对候选排序；同分时按 QID 字符串顺序决定
最高分达不到阈值就弃权，否则返回对应 QID
```

例如两个 Mercury 都精确匹配，字符串本身没有足够信息分辨行星与金属。
确定性的同分规则有利于复现，但它没有语义上的优越性。

重点看函数参数：`surface_form: str, candidates: list[StringCandidate]`。
`StringCandidate` 没有 description 和 context；这让基线不能意外多看信息。
相似度被放在 confidence 字段里方便统一输出，但它不是校准过的“正确概率”。

## 3. 对照方法：ContextGuided.resolve

文件：`disambiguation/context_guided.py`。

它没有自己实现大模型推理，而是做四件事：

1. 构造任务说明 `SYSTEM`：只选给定候选，不确定就 null，不索要隐藏思维链。
2. 构造 payload：surface、context、source_triple、候选标签/别名/描述；没有 gold。
3. 调用 `CallClient.call(..., Resolution)`，要求输出经过 Resolution 验证。
4. 检查 ID 是否在候选集合中，以及 confidence 是否达到阈值。

`CallClient` 是“请求管家”，负责缓存、调用次数、费用与输出格式。
`Provider` 是“真正去调用谁”，可以是 mock 或兼容接口。
研究方法不应直接散落着某厂商的 SDK 调用，所以把这两层分开。

在 mock 中，`providers/mock.py` 用上下文与候选描述的词语重合选实体。这是测试替身。
它不具备 GPT 的语义能力，而且简单常用词也可能影响排序；不要把它宣传成研究创新。

## 4. 串联时最重要的一段：实际选谁，就审计谁

打开 `pipeline.py`，搜索 `stage_generate_triples`。

它读取两种方法的结果，把非空的 `selected_entity_id` 合成一个去重的种子集合。
每个种子同时保存 `resolution_links`，记录它来自哪个方法、哪个 case。

假设字符串方法选到行星 Q308、上下文方法选到金属 Q925，则两者都会进入生成阶段。
不能为了后续漂亮分数把 Q308 偷偷改成 gold Q925。
如果多个别名都选到同一家公司，只为这家公司生成一次，避免重复调用。

`generation/generate_triples.py` 调用生成器，检查：

- 返回的是三元组列表，数量没有超出要求；
- 主语必须等于传入的规范标签；
- 规范化后重复的 subject/predicate/object/object_type 会被去重。

注意局限：格式和主语一致性不能保证三元组真实；后面还要审计。
生成客体写着 `object_type=entity` 也不表示它已经链接到正确 QID。

## 5. 检索与判断不能混成一步

`retrieval/wikipedia.py` 先用选中 QID 的英文 Wikipedia sitelink 找到页面。
这样比直接搜索名字更不容易拿到另一个同名实体的文章。
通过官方 API 取文本，按关系和宾语的词语重合排序段落，保留版本号、URL、时间和段落 ID。
这是一个简单可解释的检索器，不是能保证召回所有证据的语义搜索系统。

`judging/factuality_judge.py` 先调用 `prepare_evidence`：

- 重复段落只保留一份；
- 超出字符预算时跳过整段，避免截掉关键否定词；
- 没有可用证据就直接返回 NEI，不浪费模型调用。

有证据时才请求 judge。真实 prompt 明确：只依据提供的证据；没有提到不算矛盾；
无法解决的冲突选 NEI。返回后检查 evidence_ids 都来自提供的段落。
这只是防止“引用不存在段落”的程序防护，不保证引用的段落真的支持其结论。

**格式错误/模型拒绝**属于执行失败；**NEI**属于合法内容标签。这两类不能混算。

## 6. 人工工作为什么只保留一小部分？

人工在这里扮演两种角色：

- **实体复核**：确认“题目的对照答案”是否正确。首轮只核对 5 题。
- **事实盲评**：不知道 judge 的答案，读相同证据，独立给出标签。最多先做 20 条。

两者不等同，核对一个 QID 不代表核对了这个实体所有事实。
`Annotation` 中两个哈希用于确认人工和 judge 判断的确实是同一条陈述、同一批证据。
不能替换了证据还拿旧标签计算一致率。

界面固定随机抽样：`random.Random(42).sample(sorted(packet), min(20, len(packet)))`。
同一实验每次得到同一批待办；不是只选“裁判正确”的例子。样本很小且同一实体的事实相关，
因此只能作为诊断。某一标签没出现时，不要声称已经验证该标签的可靠性。

## 7. 最先会解释三个指标

1. **实体准确率**：选对 / 所有案例。弃权和失败算未选对，同时单独报告覆盖率。
2. **候选召回率**：正确 QID 在候选里的案例数 / 所有案例。用于区别检索错与排序错。
3. **人工一致率**：judge 和人类给出相同标签的条数 / 有有效双方标签的条数。
   没有人类标签时是暂无数据，不是零分。还要看缺失模型输出的覆盖率。

例子：假设 5 题选对 3 题，准确率 3/5；另外 2 题中若有 1 题没有召回正确候选，
它不能简单归咎于上下文排序。这个数字是教学示例，不是保存的实验结果。

完整公式位于 `evaluation/entity_metrics.py` 和 `judge_metrics.py`，
不必现在推导 kappa、macro F1 或置信区间；先能解释混淆矩阵的“人工为行、模型为列”。

## 8. run、cache、resume 为什么都有？

- **run** 保存一次实验的证据链。`manifest.json` 记录输入、配置和模型；`cases.json` 固定题目快照。
- **cache** 以请求内容的哈希为键，复用相同模型请求和公开 HTTP 响应，避免重复支出。
- **resume** 在新目录中继承旧实验的成功阶段；配置/代码/输入变化会拒绝继承。

主调度只有：`execute → ensure → stage_xxx`。`ensure` 先完成依赖，再运行阶段。
这不是百万级图遍历；所谓递归只是确保这几个有限步骤按依赖顺序完成。

旧实验不会随 UI 核对记录而改写。工作台的新人工标签在 `data/reviews/`，
即时对照使用已有 `agreement` 函数，不重跑模型。首次阅读可以完全跳过预算预留和缓存落盘细节。

## 9. UI 与核心代码的关系

```text
本地浏览器（HTML / CSS / 少量原生 JS）
        ↓ 读取结果 / 提交你自己的复核
workbench/server.py（只监听 127.0.0.1）
        ↓
workbench/service.py（读取已保存的 JSON；离线演示调用 Pipeline）
        ↓
已有流水线和指标函数
```

没有新增 Node 项目、React、数据库或部署需求。界面不能发起付费实验。
要定位一个 UI 显示问题才需要读 `workbench/`；讲清研究核心不需要背这些代码。

## 10. 面试练习：30 秒说明

可以用下面的结构，用你自己的话重述，别在真实实验完成前加入性能数字：

> 我实现了一个小规模知识审计原型，比较只看名字和利用上下文两种实体链接方法。
> 两种方法共享候选集合，并保留错误选择如何影响后续事实的链路。
> 生成的陈述由公开证据辅助判断，再用少量独立人工标签检查裁判错误。
> 我特别区分候选召回失败、实体选择错误、证据不足和格式失败，并保存可重放的结果。
> 目前哪些部分只是 mock、哪些经过真实实验，我会明确区分。

追问时选你真的读过的函数解释一个设计取舍：例如严格限制基线输入、NEI 不等于假，
或为什么不能用 gold 作为生成主体。比背诵 40 个文件名更有价值。
