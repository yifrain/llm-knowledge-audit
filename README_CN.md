# 从这里开始：把这个项目讲清楚

这份指南是给项目作者的学习入口，不需要先读所有英文文档。
**项目说明本来就应该解释问题、流程、实现和下一步操作。之前文档偏规范和清单，缺少教学路径，这次补齐。**

## 0. 先把工作量降下来

你现在的目标是：**理解一个可复现的小实验，能在面试中解释方法、数据、失败与局限。**
不需要先做一个完整论文级 benchmark。

| 阶段 | 你做什么 | 到这里可以停吗？ |
|---|---|---|
| 今天：理解代码和演示 | 不标注；追踪 Mercury、Java、IBM 各一个案例 | 可以，能讲清流程就有收获 |
| 首次真实试跑（2026-09-14 已完成） | 在向导中选择是否要求核对 gold；确认模型、费用与审批后运行 | 结果见下方「首次试跑事实」 |
| 小样本裁判检查 | **可选**：最多复核 20 条实际生成的事实，可分多次 | 可以，称作探索性检查 |
| 可选方法比较 | 扩展到 12 个案例，包含成对的同名异义和同义异名 | 可以，报告样本局限 |
| 更完整研究 | 40 个案例、100+ 条人工标注、更多模型与统计检验 | 以后有需要再做 |

旧的 113 条 Wikidata 练习材料**不用填写**。不要求翻译整套数据，不要求读完所有源码。
20 条标签不能支撑”模型裁判整体可靠”的结论，但可以展示评估方法，并找到具体的失败案例。

## 2. 项目到底研究什么？

输入不是一个问题“水星是什么”，而是一个**名字 + 它出现的上下文**：

```text
名字：Mercury
上下文：实验室存放着化学符号为 Hg 的液态金属。
候选：Q308（行星水星）、Q925（化学元素汞）
```

字符串方法看到名字，两个候选都很像，容易选错。
上下文方法额外看到“实验室 / Hg / 液态金属”，可以据此选择汞。
这一步叫**实体消歧（entity disambiguation）**。给实体分配 Wikidata 编号也可称为实体链接。

随后我们要求生成器围绕**它实际选中的实体**产生几条事实，找公开证据，再由另一个模型判断。
为什么还要这一步？因为**实体选对不代表后面的事实都对；关于错误实体的真事实也不算任务成功。**

### 你要先会的术语

| 术语 | 白话解释 | 例子或注意点 |
|---|---|---|
| Entity / QID | 具体实体 / 公开知识库中的编号 | Q308 是水星，Q925 是汞 |
| Surface form | 文本中写出来的名字 | Mercury，不包含实体身份 |
| Homonym | 同名异义，不一定是语音上的“同音” | Mercury 的不同含义 |
| Synonym / alias | 不同名字指同一实体 | IBM 与 International Business Machines |
| Candidate | 检索返回的可能实体 | 正确实体可能不在列表中 |
| Baseline | 用来比较的简单方法 | 只匹配标签和别名 |
| Context | 帮助判断身份的上下文 | “化学符号 Hg” |
| Triple | 主语—关系—宾语 | Java—开发者—Sun Microsystems |
| Gold | 对照答案 | 当前草稿中的 gold 必须经过人工核对才可信 |
| Mock | 可重复运行的测试替身 | 不访问大模型，也不证明大模型有效 |
| Judge | 按提供的证据分类的裁判模型 | 不是权威真相来源 |
| NEI | Not enough information，证据不足 | 没提到不等于错误 |
| Abstention | 不够有把握，放弃选实体 | 输出 null，不捏造候选编号 |
| Schema / Pydantic | 检查输出格式和字段是否合法 | 能检查 confidence 是否在 0–1，不能证明内容真实 |
| Provenance | 数据来源与版本记录 | URL、抓取时间、段落 ID |
| Cache / run / resume | 复用相同请求 / 一次实验 / 继承已完成部分 | 每次仍创建新目录，旧实验不被覆盖 |

## 3. 按什么顺序看代码？

先不用从 500 行 `pipeline.py` 的构造函数往下读。它包含很多缓存和追溯细节，容易淹没研究思路。

1. [models.py](src/llm_knowledge_audit/models.py)：只看 `EntityCase`、`Candidate`、`Resolution`、`Triple`、`Judgment`。知道输入输出长什么样。
2. [string_baseline.py](src/llm_knowledge_audit/disambiguation/string_baseline.py)：看 `normalize` 和 `resolve`。这是最容易完整理解的方法。
3. [context_guided.py](src/llm_knowledge_audit/disambiguation/context_guided.py)：看模型实际收到哪些字段，以及何时弃权。
4. [factuality_judge.py](src/llm_knowledge_audit/judging/factuality_judge.py)：看无证据、证据去重、非法引用怎么处理。
5. 最后打开 [pipeline.py](src/llm_knowledge_audit/pipeline.py)，搜索 `stage_generate_triples`，再看 `stage_judge`，理解它如何串联上面的函数。

## 4. 精确到操作：我到底要填写什么？

### A. 可选核对 gold：一屏批量确认

打开“Review / 复核 → Gold entities / Gold 实体”，选择 5 例或 12 例范围。
对照每条的上下文、gold 描述和来源链接；选择已核对的案例（可全选）。
有个别错误时，展开该行 Override，修正 QID、名称、描述或来源 URL。
填写真实复核人，明确勾选来源与实体一致，然后点击“确认所选案例”。

系统更新 `data/benchmark/pilot_cases.jsonl` 或 `starter_cases.jsonl` 中的
`verification_status`、`verified_by`、`verified_at`，保留真实批量确认记录与逐条修改前后历史，
不会把批量操作伪装成独立逐条判断。内容相同的 pilot/starter 案例同步，原始 40 例与旧运行不变。

新建运行里 **Require human-verified gold before running** 是明确选项，默认不勾选。
不要求核对时可以运行，但结果仍如实标注 gold 未经人工核对，不能声称基准已经验证。

### B. 在向导中设置真实调用

默认是 Real experiment。分别设置 resolver/generator/judge 的模型、HTTPS 接口、token 单价与上限。
价格是配置估计，审批前需核实。凭据步骤可以为三个角色填写同一服务的同一密钥，
也可填写不同服务的密钥。保存后输入框清空；清除凭据或重启服务即可移除网页输入的密钥。

最后一步明确批准所示预算与次数上限后才启动付费流程；案例确认不代表费用审批。
启动后可关闭页面，服务进程继续执行。失败续跑会重新预览并审批，始终创建新目录。
如果配置、代码或输入改变导致签名不匹配，请新建运行，不要修改旧清单绕过校验。

### C. 真实试跑后，可选复核最多 20 条事实

选择真实实验 → Review / 复核 → Facts / 事实。系统固定随机抽最多 20 条，不按模型是否选对来挑。
阅读事实和提供的证据，选择：

- **支持 / entailed**：证据支持完整陈述。
- **矛盾 / contradicted**：证据明确与陈述不兼容。
- **证据不足 / not_enough_information**：无法从这些材料确认、只有部分支持或冲突未解决。

“支持”和“矛盾”至少勾选一段引用证据；备注可空，也可写中文。
没读完就跳过，别把“没读”选成 NEI。系统自动填写时间、ID、哈希。
英文证据旁有“复制事实与证据，便于翻译”：可以翻译辅助理解，不要让模型替你冒充人工标签。

文件保存到：

```text
data/reviews/real/<当前 run-id>/human_annotations.jsonl
```

固定抽样全部标注后，运行检视才开放裁判结果与人机对照，无需重跑流水线。
只完成部分标注时，裁判结果及相关报告仍隐藏；不做标注也可运行并查看实体指标。
对照只针对这个小样本；原 `results/real/<run-id>/` 不改写。
若以后需要核心 CLI 的完整评估，备份现有配置指定的标注文件后，把这份 JSONL 内容放入该文件，再用同一配置恢复评估。
只有配置、代码和其他输入未改变时才能 `--resume`；不能恢复时保留原始实验，在工作台看小样本对照即可。

## 5. 必须是 GPT 吗？项目边界在哪里？

**不必须。研究问题与具体品牌无关。**目前代码中有两种实现：

- `mock`：离线、确定性的程序规则，用来验证流程；不能替代真实 LLM 实验。
- `openai_compatible`：调用 `/chat/completions`，当前要求 HTTPS、环境变量 API key、
  `response_format=json_schema` 的严格结构化输出，以及兼容的返回字段。

“兼容 OpenAI”是接口协议，不等于“必须用 OpenAI 的 GPT”。如果其他服务满足这些条件，
可在 `resolver`、`generator`、`judge` 分别更换 `base_url`、`model`、`api_key_env` 和真实价格。
但不能假设所有声称兼容的服务都支持严格 JSON Schema；不支持时需要补一个适配器。
本地开源模型在研究设计上完全可用，**当前适配器不是已测试完成的本地模型开箱即用支持**。
新增实现的位置是 `providers/base.py` 的 `Provider.complete`，接入点是 `Pipeline.provider`。
没必要为了一个面试项目先比较多个服务。

| 边界 | 当前做 / 暂不做 |
|---|---|
| 核心研究问题 | 上下文能否改善实体选择；小样本检查证据裁判的错误 |
| 主要评估对象 | 已知候选集合中的主体实体，以及其生成事实的证据支持 |
| 规模 | 5 例试跑、可选 12 例方法比较；人工事实复核最多先做 20 条 |
| 不做 | 模型训练/微调、百万级抓取、完整知识库建设、生产服务 |
| 不做 | 全面客体实体链接、关系/类别规范化、重现整个 GPTKB 2.0 |
| 能讲的结论 | 在这批案例、这批候选和证据上观察到什么，哪里失败 |
| 暂时不能讲 | 普遍优于其他方法、完整衡量模型知识、裁判对所有领域都可靠 |

## 6. 面试前的“我已经懂了”检查

不用背全仓库，能用你自己的话回答下面五个问题就够开始：

1. 为什么字符串基线不能看到候选描述？否则比较会发生什么变化？
2. 正确实体没有进入候选列表时，准确率下降应归因于哪里？
3. 为什么生成事实用方法实际选中的实体，而不是 gold？
4. 为什么“没找到证据”不能直接判为 contradicted？
5. 为什么 mock 高分、20 条人工一致或正确 JSON 都不等于真实模型可靠？
